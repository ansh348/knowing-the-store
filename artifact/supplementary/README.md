# Knowing the Store: anonymous supplementary material

This archive lets you check every number the paper prints, offline, on a laptop, with no API key,
regenerating a large part of them outright, and lets you see exactly how each API run was made
and what registration preceded it.

There are two paths. **Path (a) is the primary one** and is the one the archive is built around.

## What "reproduce" means here, precisely

Not every printed number is recomputed from raw data, and it would be misleading to say it is.
`reproduce_all.py` checks the paper's 14,473 numeric occurrences (4,263 distinct tokens) in four
layers, strongest first:

| layer | what happens | coverage |
|---|---|---|
| 1. recomputed from the model responses | the scoring script re-reads the per-row responses and redoes the bootstrap | `cf_pad_scores.json` offline; `para_scores.json` with the encoder (2 of the 55 score artifacts here) |
| 2. regenerated into the printed fragment | the table generator rebuilds the `.tex` from the stored scores; compared byte for byte | 15 of the 104 labelled tables and figures: **1,877 of 14,473 numeric occurrences (13%)**, 1,032 distinct tokens |
| 3. independently re-derived | the number gate reads each figure from its artifact and compares at the precision printed, not against the printed form | **176 checks, 0 mismatches**, the numbers the last three passes introduced |
| 4. accounted against a ledger | every printed numeral must appear in the ledger family, or the gate fails | **all 4,026 research-class distinct tokens, 0 unaccounted** |

Layer 4 is the weakest and its own tool says so. `trace_scan_v13.py` carries this, verbatim:

> **KNOWN LIMIT, stated so it is not mistaken for a guarantee.** Matching is set-based: a token
> counts as accounted when the string appears ANYWHERE in the ledger family, so an unrelated
> figure of equal value passes it. This is not hypothetical.

So: every printed number is **traceable to a ledger** and none is unaccounted; the numbers of the
recent passes are **independently re-derived**; about an eighth of them are **regenerated byte for
byte from the stored scores**; and two of the score files are **recomputed from the raw responses**.
The remaining score artifacts and the other 49 ledgers ship as the records they are, not as
things this script rebuilds. `REPRODUCE.md` says which of the two treatments each table gets.

## Path (a): the offline check, one command

From the directory you unzipped the archive into, the one that now contains `supplementary/`,
and with Python 3.12 or newer on your path:

```
python -m venv kts_env
# activate kts_env the usual way for your platform, then:
python -m pip install -r supplementary/requirements.txt
python supplementary/reproduce_all.py
```

Create the environment **beside** `supplementary/`, not inside it, so the archive stays exactly as
it was unpacked and `MANIFEST.sha256` still describes all of it. `reproduce_all.py` builds its
working tree at `kts_work/` beside the archive; pass `--work DIR` to put it somewhere else. It
never writes inside `supplementary/`.

That is the whole of it. `reproduce_all.py`

1. rebuilds one working tree from this archive's sections (`PATHMAP.tsv`, `DUPLICATES.tsv`),
2. checks every file against `MANIFEST.sha256`,
3. re-runs the scoring, ledger and table-fragment scripts (layers 1 and 2 above) and compares
   every output **byte for byte** with the fragment shipped here,
4. runs the paper's own number gates against `paper_v23.tex`: `r141_number_gate` (232 checks (233 inside a git checkout, where the recorded freeze date is also compared with git),
   which re-derive the pass's printed forms from their artifacts independently of the printed
   forms themselves), `trace_scan_v13` (every printed numeral accounted against a ledger) and
   `refcheck_v11` (every citation).

Exit status is the check: `0` only if everything is byte-identical and every gate passes. It
writes only inside the working directory it creates (`../kts_work` by default; use `--work DIR` to
put it elsewhere). It needs no network, no GPU, no LaTeX, and no model weights.

**One step is optional and is skipped by default.** Re-deriving `para_scores.json` from the
paraphrase check's rows needs the MiniLM encoder, because that check's lookup comparator is
encoded at scoring time and has no on-disk vector cache. The step announces itself as skipped and
names the reason; it is not a failure. Every number the paper prints from the paraphrase check is
regenerated from the stored score by the three steps that follow it, and those run without the
encoder. Install `requirements-runners.txt` if you want the deeper check as well; with the
encoder present it reproduces `para_scores.json` byte for byte. The long-list check has no such
gap, because its lookup vectors are stored, so it re-derives its scores from its rows offline.

`REPRODUCE.md` lists all 104 labelled tables and figures: which script regenerates each, what it
reads, what it writes, and for the rest, the ledger family the gates account it against.

**Python 3.12 or newer.** The reported run used 3.13.7 and an independent reviewer ran the same
check on 3.12 with the same result. `requirements.txt` is pinned to the versions the reported run
used: the float formatting of a bootstrap can differ between NumPy releases, so an unpinned
environment may produce a fragment that differs in the last digit, which is the reason for the pin.

## Path (b): how the API runs were made

Nothing here is needed for any printed number. `runners/` holds the scripts that called the
providers, `prompts/` the frozen prompt and rubric files they sent, `registrations/` the
registration that was frozen before each run together with the lock record the runner wrote at the
run's start (the registration's sha256, the model id, the cap), and `rows/` the responses that came
back, one file per lane.

Each runner reads its key from an environment variable and refuses to start without one. They are
shipped so you can read exactly what was sent, not so the runs are repeated: provider
availability, model changes and sampling mean an exact historical regeneration is not possible,
and the stored rows are the record. Model identifiers were pinned and probed before every run and
are named in the appendix.

**Requires API keys and budget; not needed for any printed number.**

## The FR-Bank release

The benchmark the experiments read is **not** redistributed here. Obtain it from the source cited
in the paper's bibliography (the `\bibitem{fr}` entry), then check your copy against the bytes the
stored scores were computed from:

```
python verify_frbank.py --path /where/you/put/LifeMemEval
```

`data/frbank_manifest.sha256` holds the sha256 of every file in it that the experiments read.

> **DOI: _to be filled in by the authors when the record is minted._** Until then the bibliography
> entry is the citation. This line is marked so it is not mistaken for an omission.

The release is cited in the third person, as prior work. Its authors' names appear in this archive
only inside that one bibliography entry; they appear nowhere else.

## The encoder

The similarity lookup that every model is compared against uses
`sentence-transformers/all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`,
weights `model.safetensors`, 90,868,376 bytes, sha256
`53aa51172d142c89d9012cce15ae4d6cc0ca6895895114379cacb4fab128d9db`. The `sentence-transformers`
library downloads it on first use, about 90 MB.

**Path (a) does not need it.** The lookup's vectors and scores are stored
(`results/cf_pad/results/lookup_vectors.json`, `results/reviews/r125/results/r125_vectors.json`
and the per-program `*_scores.json`), which is why the lookup baseline reproduces byte-exact and
why encoder drift cannot move a printed number. The encoder is needed only if you want to
re-encode from scratch, which is path (b); `requirements-runners.txt` pins the library. If the
machine you are on cannot reach the internet, place the snapshot under the
`sentence-transformers` cache directory for that revision before running anything in `runners/`.

### The backend-embedding files

Three frozen embedding files, `e2_metamemory/frbank_embeddings.npz` (66 MB),
`e1_metamemory/backend_embeddings/amem.npz` (39 MB) and `mem0.npz` (35 MB), are **not part of
this submission**. They are `.npz`, which is already compressed, so they do not shrink in an
archive: at 140 MB they are larger than the whole of the rest of this material and larger than
the upload limit on their own.

**Nothing in `reproduce_all.py` reads them**, which is why the offline reproduction passes
without them and why leaving them out costs a reviewer nothing. Their sha256 are recorded here in
`data/embeddings_manifest.sha256`, so a copy obtained later can be checked against the bytes the
experiments used. They are regenerated by `scoring/e2_metamemory/tools/embed_frbank.py` and
`scoring/e1_metamemory/tools/two_channel.py`, both shipped here; regenerating them needs the
encoder, which is `requirements-runners.txt` and path (b). If you want the files themselves
rather than regenerate them, ask in the discussion forum and the authors will post them.

Every other `.npz` the reproduction touches, the MiniLM caches and the question embeddings, is in
this archive.

## Anonymity

Author names, given names and surnames, the repository owner and name, the repository directory,
Windows and POSIX home paths, e-mail addresses and the working branch name were replaced
throughout by `[AUTHOR-1]`, `[AUTHOR-2]`, `[REPO-OWNER]`, `[REPO-DIR]`, `[PROJECTS-DIR]`,
`[HOME]`, `[EMAIL]` and `[BRANCH]`. The only exception is the FR-Bank bibliography entry described
above. The archive was scanned for all of those terms after the replacement; the scan and its
residue are reported with the build.

Three things that look like identity and are not, and were deliberately left alone:

- **Persona names and persona content.** The personas are synthetic. One of them mentions
  attending a conference; that string is data, not an author trace.
- **Third-party repository URLs**, for example the A-MEM repository the backend was run from.
  Removing them would break the attribution the appendix owes.
- **Machine timestamps inside scored data, rows and model identifiers.** A model id such as
  `gpt-4.1-mini-2025-04-14` carries a date, and every store event carries one. Rewriting those
  would corrupt the data the paper is about. Dates in prose, meaning this file, `REPRODUCE.md`, the
  registrations and the ledgers, are the registration sequence's own dates and are left as
  written, because they are the record of when each design was frozen relative to its run.

Pattern scans and review do not prove anonymity. If you find a trace, it is a defect.

## What is not here, and why

- **The FR-Bank release itself**, cited but not redistributed; see above.
- **The LongMemEval data** and every third-party benchmark corpus, licensed elsewhere.
- **Any store database.** The experiments read exported summaries and entries; no `.sqlite` or
  `.db` file is part of this work.
- **The HV-1 answer key.** The human validation was not complete at submission, and the key that
  the blind readers are scored against is sealed until scoring. Its sha256 is recorded in the
  registration; the key ships with the validation result.
- **Returned annotation workbooks.** The blank instruments are here; no returned or labelled
  workbook is, and no annotator is named. Annotators are `A1` and `A2`.
- **The writing record**: the drafting reports, the old-beside-new sign-off files, the gate logs,
  the page rasters and the interim PDFs. They are bookkeeping about the writing of the paper, not
  about the experiments.
- **Model response caches and raw provider transport logs**, beyond the scored rows.
